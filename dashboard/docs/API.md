# Darzi Register — API Reference

Base URL: the dashboard's own origin (e.g. `https://<your-app>.vercel.app`).
All request bodies are JSON and validated with Zod; invalid payloads return
`400` with a field-level error list.

Conventions:

- All timestamps are ISO-8601 strings in UTC.
- `key_hint` is the masked form of a key, e.g. `DRZ-••••-EFGH` — never
  plaintext outside server responses the client already knows.
- Admin routes require a signed-in admin session (http-only cookie set at
  `/login`). Unauthenticated → `401`; signed-in non-admin → `403`.

## Public API

No authentication. Designed for the Darzi Register mobile app.

### `POST /api/devices/register`

Register (or refresh) an app installation. Idempotent — calling it again for
the same `device_id` updates `last_seen_at` and the supplied metadata.

**Request**

```json
{
  "device_id": "a1b2c3d4e5f6",
  "manufacturer": "samsung (optional)",
  "model": "SM-A125F (optional)",
  "android_version": "13 (optional)",
  "app_version": "1.0.3 (optional)"
}
```

- `device_id` — required, string (e.g. Android `Settings.Secure.ANDROID_ID`).
- All other fields — optional strings. On repeat calls only the supplied
  fields are refreshed; `registered_at` is never overwritten.

**Response — `200 OK`**

```json
{
  "device": {
    "id": "uuid",
    "device_id": "a1b2c3d4e5f6",
    "customer_name": null,
    "manufacturer": "samsung",
    "model": "SM-A125F",
    "android_version": "13",
    "app_version": "1.0.3",
    "registered_at": "2026-10-19T16:00:00.000Z",
    "last_seen_at": "2026-10-19T16:05:00.000Z"
  },
  "is_new": true,
  "has_license": false
}
```

### `POST /api/licenses/activate`

Activate a license key on a device. **One key = one device**: a key already
bound to a different device fails with `used` (see [Error codes](#error-codes)).

**Request**

```json
{
  "key": "DRZ-AB12-CD34",
  "device_id": "a1b2c3d4e5f6"
}
```

- `key` — required. Accepted format is `DRZ-XXXX-XXXX` over `[A-Z0-9]`
  (the old admin tool's keys may contain `0`/`O`/`1`/`I`/`L`; new keys
  generated by the dashboard avoid ambiguous chars). Input is trimmed and
  uppercased before checking.
- `device_id` — required.

**Response — `200 OK`** (success)

```json
{
  "ok": true,
  "entitlement": {
    "device_id": "a1b2c3d4e5f6",
    "key_hint": "DRZ-••••-CD34",
    "expires_at": "2027-10-19T00:00:00.000Z",
    "issued_at": "2026-10-19T16:00:00.000Z",
    "sig": "<hmac-sha256-hex>"
  }
}
```

The `entitlement` is a server-signed object (HMAC-SHA256 over
`device_id.key_hint.expires_at.issued_at` with `ENTITLEMENT_SECRET`) —
store it on the device and re-verify locally, or call `/validate` for a
server-side check.

**Error responses** (JSON `{ "ok": false, "error": "<code>" }`):

| HTTP | `error` | meaning |
|------|---------|---------|
| 400 | `invalid_body` | malformed JSON / missing fields |
| 400 | `format` | key doesn't match `DRZ-XXXX-XXXX` |
| 404 | `invalid` | no such key |
| 403 | `expired` | past `expires_at` (checked before `disabled`) |
| 403 | `disabled` | key disabled by admin |
| 403 | `used` | key bound to a *different* device |
| 429 | `rate_limited` | slow down (Retry-After header) |
| 500 | `internal` | server/DB error |

### `POST /api/licenses/validate`

Re-check that a key/device pair is still valid. This is where **server-side
expiry and disable enforcement** happen: even if a device holds an
entitlement, validation consults the current row.

**Request**

```json
{
  "key": "DRZ-AB12-CD34",
  "device_id": "a1b2c3d4e5f6"
}
```

**Response — `200 OK`** (always 200; validity is in the `status` field)

```json
{ "status": "valid", "expires_at": "2027-10-19T00:00:00.000Z" }
```

`status` is one of `valid | invalid | disabled | expired`:

- `invalid` — unknown key, bad format, or key bound to a *different* device
- `disabled` — key disabled by admin (expiry is checked first)
- `expired` — past `expires_at`
- `valid` — key is good for this device (includes never-activated keys)

The only write this endpoint performs is refreshing `last_validated_at`
on a found key.

### `GET /api/licenses/status?device_id=<device_id>`

Lightweight status check for a device — the mobile app uses this on launch
to decide whether to show the app or the activation screen.

**Response — `200 OK`** (licensed device)

```json
{
  "device_id": "a1b2c3d4e5f6",
  "has_license": true,
  "status": "active",
  "expires_at": "2027-10-19T00:00:00.000Z",
  "key_hint": "DRZ-••••-CD34"
}
```

`status` follows the same precedence as everywhere else:
`expired > disabled > pending > active`. Never returns the plaintext key.

**Response — `200 OK`** (no license)

```json
{ "device_id": "a1b2c3d4e5f6", "has_license": false, "status": "none", "expires_at": null, "key_hint": null }
```

### `GET /api/health`

Public liveness probe (no auth).

**Response — `200 OK`**

```json
{ "ok": true }
```

## Admin API

Base path `/api/admin/*`. Every route enforces `requireAdmin()`:

- no session → `401 { ok: false, error: "unauthorized" }`
- non-admin user → `403 { ok: false, error: "forbidden" }`

### `GET /api/admin/metrics`

Aggregate numbers for the dashboard overview.

**Response — `200 OK`**

```json
{
  "ok": true,
  "metrics": {
    "total_licenses": 0,
    "active_licenses": 0,
    "disabled_licenses": 0,
    "expired_licenses": 0,
    "total_devices": 0,
    "activations_today": 0
  }
}
```

### Devices

#### `GET /api/admin/devices`

List known installations (newest first, paginated by query params `limit`
/ `offset`).

```json
{
  "ok": true,
  "devices": [
    {
      "id": "uuid",
      "device_id": "a1b2c3d4e5f6",
      "customer_name": "…",
      "manufacturer": "samsung",
      "model": "SM-A125F",
      "android_version": "13",
      "app_version": "1.0.3",
      "registered_at": "2026-10-19T10:00:00.000Z",
      "last_seen_at": "2026-10-19T16:00:00.000Z"
    }
  ]
}
```

#### `GET /api/admin/devices/[id]`

Single device by its UUID, including the correlated license (if any).

#### `POST /api/admin/devices/[id]/generate-key`

Generate a fresh license key **and bind it to this device**. Returns the
plaintext key **once** — it is never returned again, so hand it to the
customer immediately.

**Response — `200 OK`**

```json
{
  "ok": true,
  "key": "DRZ-AB12-CD34",
  "key_hint": "DRZ-••••-CD34",
  "device_id": "a1b2c3d4e5f6",
  "expires_at": "2027-10-19T00:00:00.000Z"
}
```

### Licenses

#### `GET /api/admin/licenses`

List license rows (newest first), with computed `status`. Query params:
`q` (searches key_hint/customer_name/device_id), `filter`
(`all|active|disabled|expired|pending`), `sort`
(`created_at|expires_at|customer_name|status`), `order` (`asc|desc`),
`page`, `per_page` (default 20, max 100). This admin-gated endpoint
includes the plaintext `key` so row actions can address the license.

```json
{
  "data": [
    {
      "key": "DRZ-AB3D-F8KQ",
      "key_hint": "DRZ-••••-F8KQ",
      "customer_name": "Ahmed",
      "device_id": "a1b2c3d4e5f6",
      "used": true,
      "enabled": true,
      "status": "active",
      "activated_at": "2026-10-19T16:00:00.000Z",
      "expires_at": "2027-10-19T00:00:00.000Z"
    }
  ],
  "page": 1,
  "per_page": 20,
  "total": 1,
  "total_pages": 1
}
```

#### `POST /api/admin/devices/[id]/generate-key`

Generate a key for a device (idempotent — returns the existing key with
`created: false` if one is already bound). `[id]` is the device's UUID.
Body: `{ "customer_name"? , "admin_note"?, "expiry": { "type": "days",
"days": 30|90|180|365 } | { "type": "custom", "date": "<ISO>" } |
{ "type": "lifetime" } }`. Returns the plaintext key **once** (201 on
create, 200 when reusing).

```json
{ "created": true, "key": "DRZ-AB3D-F8KQ", "key_hint": "DRZ-••••-F8KQ", "expires_at": "2027-10-19T00:00:00.000Z" }
```

#### `GET /api/admin/licenses/[key]`

One license row by its **full plaintext key** (URL-encoded), plus the
bound device and activation history. Admin-gated.

#### `POST /api/admin/licenses/[key]/disable` / `/enable`

Disable or re-enable a key. A disabled key fails activation and validation
with `error: "disabled"` until re-enabled.

#### `POST /api/admin/licenses/[key]/expiry`

Set (or clear) the expiry.

```json
{ "expires_at": "2026-12-31T23:59:59.000Z" }  /* or null to clear */
```

#### `POST /api/admin/licenses/[key]/cancel`

Revoke a key entirely (used → false, device unbound, disabled).

### `GET /api/admin/activity`

Recent `activation_events` (attempts, validations, activations, failures…).

```json
{
  "ok": true,
  "events": [
    {
      "id": "uuid",
      "event_type": "activated",
      "device_id": "a1b2c3d4e5f6",
      "key_hint": "DRZ-••••-CD34",
      "detail": "…",
      "created_at": "2026-10-19T16:00:00.000Z"
    }
  ]
}
```

### `GET /api/admin/audit`

`admin_audit_logs` — every admin action (who did what, when, to which
key/device). Same list shape as activity, with `actor` instead of
`device_id`.

### `GET /api/admin/settings` · `PATCH /api/admin/settings`

Read / update `app_settings` (feature flags and config the mobile app may
consume). `PATCH` takes a JSON object of key/value pairs; each change is
audited.

### `POST /api/auth/logout`

Sign out the current admin (clears the session cookies).

**Response — `200 OK`**

```json
{ "ok": true }
```

## Entitlements (signed license payloads)

An entitlement proves a device holds a valid license, signed by the server so
it can't be forged. The mobile app stores it after activation and can keep it
for offline proof; the server still re-checks expiry/disable on `/validate`.

### Format

Four dot-separated fields, the last being the signature:

```
device_id.key_hint.expires_at.issued_at.<signature-hex>
```

Example:

```
a1b2c3d4e5f6.DRZ-••••-CD34.2027-10-19T00:00:00.000Z.2026-10-19T16:00:00.000Z.9f2c…a1
```

### Signing

- **Algorithm:** HMAC-SHA256, key = `ENTITLEMENT_SECRET` (server-only).
- **Message:** the literal string
  `device_id.key_hint.expires_at.issued_at`
  (the four fields joined with `.`, exactly as they appear in the payload).
- **Signature:** hex-encoded HMAC digest, appended as the fifth field.

### Verify (pseudo-code, server side)

```text
function verifyEntitlement(entitlement, secret):
    parts = entitlement.split(".")
    if parts.length != 5: return INVALID
    device_id, key_hint, expires_at, issued_at, signature = parts

    expected = HMAC_SHA256(key=secret, message=join(".", [device_id, key_hint, expires_at, issued_at]))

    if not constant_time_equal(signature, hex(expected)): return INVALID
    if now() > parse_time(expires_at): return EXPIRED
    # then load the license row by key_hint / key_hash and check enabled + device binding
    return VALID
```

Notes:

- Always compare signatures in constant time.
- An entitlement that verifies cryptographically is still subject to the
  live row: a key disabled or expiry-changed by an admin after issuance
  fails `/validate` — the signature is proof of issuance, not of current
  validity.
- Never send `ENTITLEMENT_SECRET` to the client; the mobile app cannot and
  need not verify signatures itself.

## Error codes

Returned as `{ "ok": false, "error": "<code>" }` (often with `key_hint`).

| Code       | Meaning                                                      |
|------------|--------------------------------------------------------------|
| `format`   | Key doesn't match `DRZ-XXXX-XXXX` (wrong chars/length).      |
| `invalid`  | Key format is fine but no such key exists.                   |
| `used`     | Key is already bound to a *different* device.                |
| `disabled` | Key disabled by an admin (re-enable to restore).             |
| `expired`  | `expires_at` is in the past (admin can extend/clear).        |
| `network`  | Client-side only: the request never reached the server.      |

HTTP semantics: malformed request bodies → `400`; admin auth failures →
`401`/`403`; everything else about license state is carried in the `error`
field on a `200` response so mobile clients can switch on one code path.

## Rate limits

- **Login:** 10 attempts per 10 minutes per IP (in-memory per server
  instance). Exceeding it returns `429`.
- **API routes:** no dedicated per-endpoint rate limiting is configured at
  this time. If abuse is observed, the intended upgrade path is Upstash Redis
  (`@upstash/ratelimit`), the same library noted for the login limiter —
  see the comment in `app/login/actions.ts`.

## activation_events event types

The `activation_events` table records every license/device-relevant event.
Observed `event_type` values (exactly as emitted by the implementation):

| event_type           | Emitted when                                   | outcome values |
|----------------------|------------------------------------------------|----------------|
| `device_registered`  | `POST /api/devices/register` runs              | `success` |
| `activation_succeeded` | a key is successfully bound to a device      | `success` |
| `reactivation`       | same-device re-activation                      | `success` |
| `activation_failed`  | an activation attempt fails                    | `format`, `invalid_key`, `disabled`, `expired`, `already_used`, `db_error`, `conflict`, `config_error` |
| `key_generated`      | an admin generates a key                       | `success` |
| `license_disabled`   | an admin disables a key                        | `success` |
| `license_enabled`    | an admin enables a key                         | `success` |
| `expiry_changed`     | an admin changes a key's expiry                | `success` |

`license_key_hint` is always the masked form (`DRZ-••••-EFGH`) — never plaintext.
`actor_type` is `app` for public routes, `admin` for admin actions.

## Mobile app adoption

**Status: the current React Native app talks to Supabase PostgREST directly
and KEEPS WORKING unchanged.** It GETs the license row by key and, on
activation, PATCHes `used=true`, `device_id`, `activated_at` onto the row
with the anon key. None of that is touched by this dashboard; the permissive
anon RLS policies on `licenses` are intentionally left in place
(see `supabase/RLS.md`) so the live app cannot be bricked.

To adopt the new dashboard API, the mobile app must:

1. **Point at the dashboard URL** for license traffic instead of
   `<supabase-url>/rest/v1/...`.
2. **Call `POST /api/licenses/activate`** (body: `{ key, device_id }`)
   instead of PATCHing the `licenses` row directly.
3. **Verify and store the entitlement** returned by `/activate` (an
   HMAC-signed `{device_id, key_hint, expires_at, issued_at, sig}`
   object) — keep it for offline proof of license. Re-check with
   `POST /api/licenses/validate` while online.
4. **Call `POST /api/devices/register`** on first launch (and periodically)
   with `{ device_id, manufacturer, model, android_version, app_version }`
   so the device shows up in the dashboard's Devices view.

### Exact behavioral differences (new API vs. direct Supabase)

- **Server-side expiry enforcement:** direct PATCH activation never checks
  `expires_at`; `/activate` and `/validate` do — an expired key is rejected
  with `error: "expired"`.
- **Server-side disable enforcement:** direct PATCH ignores the `enabled`
  flag; the new API rejects disabled keys with `error: "disabled"`.
- **Signed entitlement:** direct Supabase writes return no proof of license;
  the new API returns a signed entitlement (HMAC-SHA256, `ENTITLEMENT_SECRET`)
  that the device stores and the server re-verifies.
- **Single-device binding enforced:** direct PATCH can overwrite `device_id`
  on a used key; `/activate` refuses with `error: "used"` when the key is
  already bound to another device.
- **Audit trail:** every attempt, activation, and validation through the new
  API is written to `activation_events`; direct Supabase traffic is not
  logged there.

Only after **all** installed apps have moved to the new API (confirm via
`activation_events` and `devices.app_version`) may the anon policies on
`licenses` be tightened to service-role-only — see the step-by-step plan in
`supabase/RLS.md`.
